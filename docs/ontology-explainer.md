# Ontology 入门与面试说法

## 定义

ontology 是一份领域定义文件。它写清四件事：

1. 有哪些类（仓库、物料、库存、批次、在途、订单）
2. 每个类有哪些属性（仓库有 id、名称、类型）
3. 类之间有什么关系（库存位于仓库、库存包含批次、物料可替代）
4. 指标和规则怎么算怎么判（可用量的公式、临期批次不能承诺）

它不存数据。数据存在 MySQL、Neo4j、Milvus 里。

## 和知识图谱的关系

ontology 是定义，知识图谱是按这个定义装进去的数据。

举例。ontology 里有这句话：批次有过期天数，保税仓有清关状态。知识图谱里就有这样的节点：批次 B-HK-X1C-01，过期 240 天，清关状态 0，位于香港保税仓。

## 为什么要有它

同样一个「可用库存」，销售、计划、仓管三个部门的算法不一样，而且这个差异没有任何文档记录。把口径写进 ontology 之后，代码去读文件算数，口径有了版本，也能改。

## 代码怎么用它

不需要 OWL 推理机。本项目的做法是把公式和规则写成 YAML，工具层解析这个文件：

- `metrics.available_inventory.formula` 交给一个小的表达式求值器，变量从 MySQL 行里取。
- `rules` 每条形如「条件满足则排除批次或排除仓库」，条件匹配器读 `when` 里的键。
- 命中哪条规则会写进返回结果，前端展示。

这样做的好处是 ontology 真的在查询链路上执行，不是一张图。

## 面试可能被问

**问：你的 ontology 和一张建表语句有什么区别？**

答：表只有结构，没有口径和规则。ontology 里有可用量的公式、有临期批次不能承诺这条规则、有规则被哪份合同覆盖的版本信息，而且代码会读它。

**问：为什么要用 YAML 不用 OWL？**

答：OWL 的表达力更强，推理也更完整，但这个场景的规则是简单的条件判断，YAML 能让人直接读、直接改，成本低。要换成 OWL，把这个文件当唯一事实来源，换掉解析层就行，上层不动。

**问：改 ontology 会影响历史查询吗？**

答：会，所以每次回答都带上 ontology 版本号，历史结果可以区分是按哪个版本算的。

**问：那规则冲突了怎么办？**

答：文件里 `conflicts` 段记录了同一指标在不同视角下的口径，以及按问题类型选哪个口径。冲突不留给模型猜。
